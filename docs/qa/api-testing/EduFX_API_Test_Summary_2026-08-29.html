01Executive summary

The EduFX API service is reachable — the health check, OpenAPI contract and Swagger UI all respond correctly. However every endpoint that touches the database fails at runtime with:

{"success": false,
 "message": "Unexpected error: [Errno -2] Name or service not known",
 "data": null}

This is a DNS resolution failure (getaddrinfo) inside the container when the Supabase client opens its connection. Because data_backend is set to supabase, there is no in-memory fallback, so 15 endpoints are non-functional and the remaining test scope is blocked behind them.

What was verified and passes: request validation (all 422 cases), authentication rejection on protected routes (401), the internal-reminder shared-secret gate (403), routing and HTTP-method handling (404 / 405), and contract accuracy against the SQA endpoint list.

What could not be verified: login, diagnostic placement, content delivery, quiz retrieval & AI generation, quiz scoring, progress tracking, behaviour storage, AI teacher chat/report, admin actions, and — critically — student data isolation.

05Defect log

DEF-001 Backend cannot reach its database; all data endpoints return HTTP 500 Critical
Status
New → Open
Affected
15 endpoints directly · 30 planned checks blocked · entire functional scope
Reproducibility
100% — retried 6× over 30s and across the full run

Steps: GET /content/subtopics → 500, body {"success":false,"message":"Unexpected error: [Errno -2] Name or service not known","data":null}. Identical for /progress/1, /diagnostic/questions, POST /auth/google (valid demo token), /teacher/1/report, and every other data-backed route.

Analysis: [Errno -2] Name or service not known is a DNS failure raised when the Supabase client connects. data_backend=supabase with no in-memory fallback once that mode is selected, so every repository call fails. Health survives because it touches no repository.

Cross-check: the previous backend URL (edufx-backend-rngcuc5r2a-an.a.run.app) shows the identical failure on the same endpoints. Both deployments are affected → this is a Supabase project-level outage (paused / deleted / free-tier auto-pause), not a single bad revision. Fix is on the Supabase side, or switch the deploy to data_backend=memory.

Impact: students cannot log in, take the diagnostic, load content, take quizzes, view progress, or use the AI teacher; the admin console is non-functional.

Retest when fixed: all 30 blocked checks plus the functional / boundary / isolation / AI-relevance suites never reached.

DEF-002 Internal exception details leaked in the 500 response body Medium
Status
New → Open
Affected
Global generic exception handler

The catch-all handler returns f"Unexpected error: {exc}" to the client, exposing the raw OS error string and the fact that the backend depends on an external host. The SQA §14 risk register requires "controlled API error responses" — this control fails. Return a generic message and log detail server-side only.

DEF-003 Student data endpoints have no authentication or ownership enforcement Medium → Critical if confirmed
Status
New → Open — behaviour blocked by DEF-001; raised from contract + code review
Affected
scheduler, content, quiz, results, explanation, progress, behaviour, settings, teacher, auth/check

None of these routes take a bearer token or verify the caller against the student_id in the path/body/header. IDs are sequential integers, so any client that guesses one could read another student's progress, quiz results, answer explanations, behaviour/proctoring history and settings, and post data or chat as them. Cross-account checks IS-01…IS-03 were designed to prove this but returned 500, so the finding is unverified against the live API and must be retested once DEF-001 is fixed. The SQA §14 register scores this scenario Critical.

DEF-004 CORS allows credentialed requests from any *.run.app origin Low
Status
New → Open

allow_origin_regex = https://.*\.run\.app with allow_credentials=True. Verified:

OPTIONS /progress/1   Origin: https://attacker-abc123.run.app
→ 200  access-control-allow-origin: https://attacker-abc123.run.app
       access-control-allow-credentials: true

Any site deployable to Cloud Run is treated as a trusted browser origin. Tighten the regex to the specific frontend hostname(s). Impact is limited because the API auth token travels in a header, not a cookie.

DEF-005 demo: bearer token bypasses authentication and is not flag-gated Low
Status
New → Open

Any request with Authorization: Bearer demo:<name>:<email> is accepted as that identity with no credential check, and the bypass is not guarded by the demo_mode setting, so it cannot be disabled by configuration. Gate or remove it before storing real user data.

07Positive observations

Working correctly — no defect

  • Input validation is solid. All 20 malformed-request checks returned 422 with a proper validation body — missing bodies, missing required fields, wrong scalar types, invalid enums (rating, session_length, choice, chat role), and non-numeric path parameters.
  • Authentication rejection is correct. POST /auth/google and every /admin/* route return 401 for missing or malformed Authorization headers, before any backend work.
  • Internal reminder endpoint is protected. POST /internal/reminders/run returns 403 for both a missing and an incorrect x-internal-secret.
  • Routing & method handling are correct. Unknown routes 404; disallowed methods 405.
  • Contract is published and accurate. /openapi.json and /docs load; the 27 documented paths match the SQA §7 list exactly.

09Recommendation

Not ready for release.
  1. Fix DEF-001 first. Restore the Supabase project / correct SUPABASE_URL / fix Cloud Run egress. Until a data endpoint returns 2xx, no further functional QA is possible. Interim option: deploy with data_backend=memory so the API is at least demonstrable.
  2. Hand back for a full functional pass. QA re-runs the 30 blocked checks plus the positive / boundary / business-logic / cross-account / AI-relevance suites never reached — quiz scoring, progress updates, diagnostic level placement, behaviour aggregation, admin RBAC actions, AI chemistry-relevance sampling.
  3. Resolve DEF-003 before storing real student data — highest-impact design gap and a Critical risk in the SQA plan.
  4. Fold DEF-002, DEF-004, DEF-005 into the same hardening pass.

Estimated QA effort after DEF-001 is fixed: ~3 days (matches the unused SQA §16 "API test execution" allocation).
